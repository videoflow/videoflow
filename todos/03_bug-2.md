# Missing BATCH Jobs audit — 2026-09-20

Reviewed against videoflow core commit `73e3b84`.
**Status: Still valid.** Confirmed reporting defect requiring a fix. The redesign added
useful Job failure and scheduling checks, but completion still treats an empty
observed Job set as success. A failed Kubernetes API query can take the same
incorrect path.

## Evidence

`wait_for_completion()` builds `pending` and `failed` exclusively from Jobs
returned by the current query. It skips the provision Job and returns an empty
failure list whenever no observed Job remains pending:
[kubernetes.py](../videoflow/engines/kubernetes.py#L481).
It does not compare the observation against the expected worker Job set or
require terminal-success evidence for every expected node. Deleting all worker
Jobs reproduces the historical case; deleting an unfinished subset can also
produce false success once the remaining observed Jobs complete.

Separately, `_job_states()` runs `kubectl get jobs` with `check=False` and parses
stdout without checking `returncode`:
[kubernetes.py](../videoflow/engines/kubernetes.py#L316).
An API/RBAC/connection failure with empty stdout becomes the same empty Job set.
The BATCH deployment path prints `Flow ... completed.` when the resulting
failure list is empty and no stall was recorded:
[cli.py](../videoflow/deploy/cli.py#L765).

The redesign does correctly distinguish failed **attempts** from terminal Job
failure by reading `Complete`/`Failed` conditions:
[kubernetes.py](../videoflow/engines/kubernetes.py#L299).
That fix should be preserved; it does not solve missing Jobs or failed reads.

## Reproduction and required follow-up

Two isolated in-memory probes called the actual `wait_for_completion()` method
with flow/run IDs set. One replaced `_job_states()` with an empty result; the
other replaced the subprocess response with `returncode=1`, empty stdout and
stderr `Forbidden`. Both incorrectly returned success:

```text
deleted_jobs_completion_result: []
kubectl_api_failure_completion_result: []
```

No cluster was contacted and no Jobs were deleted. The direct method results
were reproduced; the CLI completion consequence was verified from its code.

Required follow-up:

- Track the expected worker Jobs for the run and require confirmed successful
  completion of every expected Job. Treat a missing unfinished Job as a failed
  or indeterminate run, rather than inferring success from an empty query.
- Preserve verified terminal completion evidence if completed Jobs are later
  reaped; make initial absence and later deletion distinguishable from success.
- Surface failed or unparseable API observations explicitly. A retry/grace
  policy may tolerate transient failures, but an unobserved run must not be
  reported complete.
- Add regressions for all Jobs deleted, one unfinished Job deleted, only the
  provision Job present, API denial/unavailability, and all expected Jobs truly
  complete. Retain tests that allow a Job to retry after a failed pod.

## Validation performed

The mocked probes above confirmed the defect independently of the test suite.
The related runtime/unit selection, including
[test_k8s_watchdog.py](../tests/test_k8s_watchdog.py#L1) and
[test_batch_lifecycle.py](../tests/test_batch_lifecycle.py#L1), completed with
**209 passed, 1 failed**. The failure was the unrelated macOS Docker-URL
expectation in `test_local_engine.py`; its isolated rerun also failed.
A model/process conformance selection completed with **9 passed, 16 deselected**.
The exact commands and failure explanation are in
[01_small_bugs.md](01_small_bugs.md#validation-performed).
No live broker, Kubernetes, or GPU integration verification was performed, and
no application fix was made during this audit.
